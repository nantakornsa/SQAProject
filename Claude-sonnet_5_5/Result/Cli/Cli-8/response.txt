Correction: `HelpFormatter.DEFAULT_NEW_LINE_PLACEHOLDER_FIX` does not exist, so the version above will not compile. Here is the compilable version, which uses the `line.separator` system property that `HelpFormatter` uses for its default newline:

```java
package org.apache.commons.cli;

import junit.framework.TestCase;

/**
 * Regression test for CLI-151: wrapped continuation lines were computed
 * with the padding offset, so padded lines could exceed the width.
 */
public class HelpFormatterWrapRegressionTest extends TestCase
{
    public void testPrintWrappedPaddedContinuationLines()
    {
        int width = 20;
        int padding = 4;
        String nl = System.getProperty("line.separator");
        String text = "aaaa bbbb cccc dddd eeee ffff gggg hhhh";
        String expected = "aaaa bbbb cccc dddd" + nl
                + "    eeee ffff gggg" + nl
                + "    hhhh";

        StringBuffer sb = new StringBuffer();
        new HelpFormatter().renderWrappedText(sb, width, padding, text);
        assertEquals("padded continuation lines must be wrapped at the width", expected, sb.toString());
    }
}
```

On the buggy version, the second line `"    eeee ffff gggg hhhh"` is 23 characters. `findWrapPos` is called with `startPos = 4`, so it sees `4 + 20 >= 23` and returns -1 without wrapping. The fixed version starts the search at 0 and wraps correctly, so the test fails before the fix and passes after it.

I did not compile or run this test. The expected string comes from tracing `findWrapPos` by hand against my recollection of the commons-cli 1.1 source.
